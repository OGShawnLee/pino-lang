# D-188: `pino test`, rich `assert` failure output, and per-test leak reporting

Status: accepted
Raised by: 080
Feature: spec/features/testing.md

## Question
How does `pino test` discover, isolate, run, and report `test "name" { }` blocks, how do failing `assert` statements format their output, and how are per-test memory leaks handled?

## Evidence
- `test "name" { }` blocks and `assert(<cond>[, <msg>])` are already parsed (`TestDeclarationSyntax`, `AssertStatementSyntax`) and type-checked (`BodyChecker.CheckTest`, `BodyChecker.CheckAssert`), while `IrLowerer` previously skipped `TestDeclarationSyntax` and lowered `assert` to a generic `"Assertion failed."` panic.
- Ticket 074 (`pino init`) generates `test/main_test.pino` containing `test "should add numbers correctly" { assert(add(2, 3) == 5) }` and installed a temporary placeholder message for `pino test`.
- `spec/features/modules.md` (`MOD-8`, `D-064`, `D-163`) already defines test files (`*_test.pino` or files inside `test/`) for `@@Testable` imports.
- `pino-csharp-re` has two IR engines: `Pino.Vm` (with shadow reference-count leak tracking) and `CodeGen/C` (compiled with `-DPINO_DEBUG_RC` for native leak tracking).

## Options
1. Introduce dedicated assertion helpers (`assert_eq`, `assert_lt`, ...) or keep a single `assert` statement whose compiler-generated panic message displays operand values on comparisons.
2. Stop the whole test run on the first failure vs. stop only the failing test and continue running remaining tests and files.
3. Fail on leaks immediately vs. warn by default and turn leaks into failures under `--strict`.
4. Add expected-panic test syntax now vs. defer it past 0.4.

## Decision
Decided by the owner on 2026-11-24:
1. **A failing `assert` shows the values involved**, pytest-style, generated by the compiler. There is no new assertion function to learn. This applies to every `assert`, both inside `test` blocks and in normal programs.
2. **The first failed `assert`, or any panic, stops that test only.** The remaining tests in the file and the remaining files still run.
3. **Leaks warn by default.** `--strict` turns a leak into a test failure (`error:` instead of `warning:`). Leaked objects are listed one per line below the test's result line, not on a single line.
4. **Expected-panic tests are not in 0.4.** No syntax for them is added.
5. **CLI help must list every command and option** (enforced by the shared command/option table and help guard test from ticket 074), written in plain words without compiler jargon.

Note (2026-11-24, ticket 082): value lines are no longer indented beyond the "was false" line (owner).
