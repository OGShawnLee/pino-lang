# Functions, lambdas, closures

Status: tree-walk 18/18 | VM 11/18 | C 11/18   (from conformance/STATUS.md)

## Syntax
Grammar productions: see `spec/grammar.ebnf` section `fn`.
A function is declared with `fn`, a name, a parameter list (`[mut] name Type` pairs, parentheses optional when empty), an optional return type and a braced body; parameters are deeply immutable unless marked `mut`, and `mut` parameters require `mut` at every call site (`name(mut a)`). A lambda is an anonymous function expression written `fn (params) -> expr` or `fn (params) { ... }`. Function types are written `fn ([mut] T1, [mut] T2) -> R` (parentheses optional when empty, omitted return means `void`, so `fn` alone is `fn () -> void`). The reference has no dedicated functions section; the rules below come from the function syntax used in its other sections and from the tests.

## Rules
- FN-1: `fn name(p1 T1, p2 T2) { ... }` declares a function with typed parameters that are deeply immutable by default; mutable parameters are declared `mut p T` and require `mut` at every call site (`name(mut a)`). [src: ParserTests.TestParseFunctionDeclaration; ScopingExecutionTests.TestScopeLeakageFromCallerToCalleeExecution; spec/decisions/D-180-mut-parameters-calls-and-closures.md]
- FN-2: A return type is written after the parameter list: `fn add(a int, b int) int { ... }`. [src: LANGUAGE_REFERENCE.md §7 "Structs" (`distance_to`); LANGUAGE_REFERENCE.md §8 "Error Handling" (`divide`); ScopingExecutionTests.TestScopeLeakageFromCallerToCalleeExecution]
- FN-3: `return expr` ends the call and the call expression evaluates to `expr`. [src: ParserTests.TestParseFunctionDeclaration; ScopingExecutionTests.TestScopeLeakageFromCallerToCalleeExecution]
- FN-4: The parentheses of the parameter list may be omitted when a function has no parameters, as in `fn name { ... }`. [src: ScopingExecutionTests.TestScopeLeakageFromCallerToCalleeExecution; ParserTests.TestParseStructDeclaration]
- FN-5: Commas between parameters are optional. [src: LANGUAGE_REFERENCE.md §1 "Syntax Guidelines"]
- FN-6: Commas between call arguments are optional. [src: LANGUAGE_REFERENCE.md §1 "Syntax Guidelines"]
- FN-7: A function with an empty parameter list `()` is declared and called with empty parentheses. [src: ScopingExecutionTests.TestScopeLeakageFromCallerToCalleeExecution; CheckerTests.TestTypeCheckerTupleValid]
- FN-8: `fn (params) -> expr` is an expression whose value is a function that returns `expr`. [src: LANGUAGE_REFERENCE.md §10 "Vector Methods" (`map`); DataStructureTests.TestStructLambdaFieldExecution; spec/decisions/D-100-arrow-token.md]
- FN-9: `fn (params) { ... }` is an expression whose value is a function with a block body that uses `return`. [src: LANGUAGE_REFERENCE.md §10 "Vector Methods" (`each`)]
- FN-10: A lambda with no parameters is written `fn () -> expr`. [src: ScopingExecutionTests.TestLambdaCaptureScopingExecution; spec/decisions/D-100-arrow-token.md]
- FN-11: A function value, whether a lambda or the name of a declared function, can be stored in a variable, passed as an argument and called through that variable or parameter. [src: ScopingExecutionTests.TestLambdaCaptureScopingExecution; DataStructureTests.TestStructCallableFieldsAndBoundMethods; CheckerTests.TestTypeCheckerTupleReturningFunction]
- FN-12: The type of a function value is written `fn (T1, T2) -> R`, carrying per-parameter `mut` qualifiers (`fn (mut T1, T2) -> R`), and `fn (mut T) -> R` is distinct and non-convertible from `fn (T) -> R`. [src: DataStructureTests.TestStructCallableFieldsAndBoundMethods; StdlibTests.TestCustomGenericShorthandLambda; spec/decisions/D-101-function-type-syntax.md; spec/decisions/D-180-mut-parameters-calls-and-closures.md]
- FN-13: A function may declare a function type as its return type and return a function value, as in `fn get_adder() fn (int) -> int { ... }`. [src: CheckerTests.TestTypeCheckerTupleReturningFunction; LANGUAGE_REFERENCE.md §3 "Labeled Tuples (Return-Exclusive)"; spec/decisions/D-101-function-type-syntax.md]
- FN-14: A function declaration may appear inside another function's body, and it is callable from that body. [src: CheckerTests.TestTypeCheckerTupleReturningFunction]
- FN-15: A lambda can read the variables of the scopes enclosing it, including the locals of the enclosing function and of an enclosing block. [src: ScopingExecutionTests.TestLambdaCaptureScopingExecution]
- FN-16: A call argument that uses the undeclared name `it` is an implicit lambda with the single parameter `it`, so `xs:filter(it:len <= 4)` filters by that expression. [src: ParserTests.TestImplicitLambdaArgumentWrapping; StdlibTests.TestShorthandLambdaItResolution; LANGUAGE_REFERENCE.md §10 "Vector Methods" (`count`)]
- FN-17: When `it` is declared as a parameter of the enclosing function, an argument using `it` refers to that parameter and is not turned into a lambda. [src: ParserTests.TestNoImplicitLambdaWrappingWhenDeclared]
- FN-18: A called function does not see the local variables of its caller. [src: ScopingExecutionTests.TestScopeLeakageFromCallerToCalleeExecution]
- FN-19: A `val` declared in an inner block shadows an outer variable of the same name inside that block only, and the outer binding is visible again after the block. [src: ScopingExecutionTests.TestScopeShadowingInLocalBlocksExecution]
- FN-20: In a function type, parentheses may be omitted when there are no parameters (`fn -> R`), per-parameter `mut` precedes the parameter type (`fn (mut T) -> R`), and an omitted return type means `void`, so `fn` alone is `fn () -> void` and `fn (mut T)` is `fn (mut T) -> void`. [src: spec/decisions/D-101-function-type-syntax.md; spec/decisions/D-180-mut-parameters-calls-and-closures.md]
- FN-21: Closures capture enclosing `var` and `val mut` bindings that they mutate by reference per closure instance (both direct reassignment of a `var` and interior mutation of a `var` or `val mut` count as mutation), so mutations persist across calls to that closure without affecting other instances, while captured `val` bindings are captured deeply immutably by value. [src: spec/decisions/D-056-closure-mutable-capture.md; spec/decisions/D-180-mut-parameters-calls-and-closures.md; spec/decisions/D-183-val-mut-and-module-state.md]

- FN-22: `return` at the end of a line continues onto the next line like a trailing binary operator, and is bare (returns `void`) only when the next token is `}` or end of file. [src: spec/decisions/D-142-return-newline-continuation.md]
- FN-23: A line break before `(` ends the preceding expression, so a call's `(` must appear on the same line as its callee. [src: spec/decisions/D-144-newline-before-open-paren.md]
- FN-24: Untyped lambda parameters must be separated by commas (`fn (n, m) -> n + m`), whereas typed parameters remain comma-optional, so `fn (n m)` declares one parameter `n` of type `m`. [src: spec/decisions/D-145-untyped-lambda-param-commas.md]
- FN-25: Calling an indexed expression such as `fns[0](9)` calls the indexed element when the brackets contain an expression rather than type arguments. [src: spec/decisions/D-055-indexed-element-call.md]

- FN-26: Declarations (`fn`, `struct`, `enum`, `union` and `interface`) are hoisted at module level and inside nested blocks, so they can be used before their textual position in the same scope; `val` and `var` are not hoisted. [src: spec/decisions/D-165-declaration-hoisting.md]
- FN-27: A named function without a declared return type has the type of its `return` statements as its return type, and is `void` when it has no value-returning `return`. [src: spec/decisions/D-050-function-return-type-inference.md]
- FN-28: Return-type inference does not depend on the order of the base case and a recursive call, so `if n > 0 { return n * f(n - 1) } return 1` infers `int` just as the early-base-case form does, and mutual recursion works in any declaration order. [src: spec/decisions/D-050-function-return-type-inference.md]
- FN-29: When one `return` of an unannotated function yields `float` and the others yield `int`, the inferred return type is `float`. [src: spec/decisions/D-050-function-return-type-inference.md; spec/decisions/D-019-int-float-mixing-and-division.md]
- FN-30: Untyped lambda parameters take their types from the context the lambda appears in: a typed `val` or `var`, a `return` in a function with a known return type, a struct field type, a collection element type or a call argument. [src: spec/decisions/D-167-lambda-parameter-inference.md]
- FN-31: A single `mut` argument or mutating receiver combined with one or more read-only arguments rooted at the same binding (such as `f(mut a, a)`, `v:push(v[0])`, or `p:add(p:x)`) is allowed; the read arguments are evaluated as values left to right before the call's mutable access begins. [src: spec/decisions/D-180-mut-parameters-calls-and-closures.md]
- FN-32: Two `mut` accesses in the same call that share a root binding are allowed with no diagnostic and no run-time check when their place paths are proven disjoint by differing at a field step (`p:x` vs `p:y`) or at an index step whose index expressions are proven different (FN-33). [src: spec/decisions/D-184-disjoint-mut-slots.md]
- FN-33: Index expressions at the same depth of two place paths are compared syntactically without constant folding and with parentheses unwrapped: integer literals (including unary `-` on an integer literal) are proven equal when their values match and proven different otherwise; non-interpolated string literals are proven equal when their texts match and proven different otherwise; literals of other types (`bool`, `rune`, `float`, enum members) are unknown; `n`, `n + k`, and `n - k` for the same immutable binding symbol `n` (`val` not `val mut`, non-`mut` parameter, loop variable per D-182, pattern binding, or `it`; never `var`, `val mut`, `mut` parameter, or field) and integer literal `k` are proven equal when their net offsets match (for any index or key type) and proven different when their net offsets differ (for `int` indexes only); two distinct immutable bindings `a` and `b` compared by resolved symbol are proven different inside the then-branch of an `if` statement or `if` expression whose entire unwrapped condition is `a != b` or `b != a` (holding through nested `if`s, loops, and blocks, but not inside lambda bodies, `else` branches, after the `if`, or for `and`/`or` conditions); all other forms are unknown. [src: spec/decisions/D-184-disjoint-mut-slots.md]
- FN-34: When two `mut` accesses in a call share a root binding and are neither proven disjoint (FN-32) nor proven overlapping (FN-E16), the call is accepted by the checker and requires a run-time exclusivity check over their list of unknown index-step pairs: after all arguments are evaluated and their slots resolved (with any absent map key in `mut m[k]` panicking first per MAP-E1) and before the callee runs, the two places alias only if every unknown step pair resolves to the same slot address at that prefix depth; if they alias, the program panics (ERR-3, exit code 101 per ERR-5) with `Cannot pass the same element of '<collection>' as two 'mut' arguments to <target>.`, where `<collection>` is the first identifier of the path as written at the call site (`enemies` for `enemies[i]`, `items` for bare field `items[i]`, `self` for `self:items[i]`) and `<target>` is the unqualified function or method name as written at the call site in single quotes (`'duel'` for `duel(...)`, `Mod::duel(...)`, `x:duel(...)`) or the unquoted words `this function` for a call through a function value. [src: spec/decisions/D-184-disjoint-mut-slots.md]
- FN-35: Call-site `mut` exclusivity (FN-E16, FN-32, FN-33, FN-34) applies pairwise to every pair of `mut` accesses in a call that share a root binding, including mutating method receivers with their full place path (or `self` with no steps for an implicit-`self` sibling method call) and bare fields inside methods modeled as `self` followed by `:field`. [src: spec/decisions/D-184-disjoint-mut-slots.md]
- FN-36: A `mut` parameter can be reassigned inside the function, and the caller's variable then holds the new value, because a `mut` parameter is the caller's own variable (`inout`) per D-180; this is how `fn swap(mut a int, mut b int)` works. [src: spec/decisions/D-180-mut-parameters-calls-and-closures.md]
- FN-37: A `mut` argument must have exactly the parameter's type, with no `int` to `float` widening and no struct to interface conversion, because the callee may assign any value of the parameter's type (for example another struct that implements the interface) into the caller's variable, which must be able to hold it; otherwise the checker reports `PN3102` with `A 'mut' argument must have exactly the parameter's type '<ParamType>', but '<name>' is '<ArgType>'.` and help `declare '<name>' with type '<ParamType>', for example 'var <name> <ParamType> = ...'`. [src: spec/decisions/D-180-mut-parameters-calls-and-closures.md]

## Errors
- FN-E1: Calling a function with an argument of the wrong type is rejected with a type check error. [src: CheckerTests.TestEnumDefinitionAndTypeChecking; CheckerTests.TestRuneTypeChecker]
- FN-E2: Named functions and methods must have block bodies (`{ ... }`); an arrow body on a named function or method (`fn f() int -> 1`) is rejected as a parse error. [src: spec/decisions/D-052-arrow-bodied-function-declarations.md]
- FN-E3: A lambda with an explicit return type (`fn (n int) int -> n`) is rejected as a parse error. [src: spec/decisions/D-053-lambda-return-type-annotation.md]

- FN-E4: Recursion in an unannotated function with no non-recursive `return` is rejected by the checker with a message containing "explicit return type". [src: spec/decisions/D-050-function-return-type-inference.md]
- FN-E5: `return` statements of an unannotated function whose types differ, apart from `int` with `float` (FN-29), are rejected by the checker with a message containing "conflicting return types": `int` with `string`, `bool` with `int`, two different struct types, and a struct with an interface alike; a declared return type is how a function returns an interface. [src: spec/decisions/D-50-function-return-type-inference.md]
- FN-E6: A function whose return type is not `void` and that does not return on every path is rejected by the checker with a message containing "always return". [src: spec/decisions/D-050-function-return-type-inference.md]
- FN-E7: A bare `return` in a function whose return type is not `void`, whether it is declared or inferred from the function's other `return`s, as in `fn f(b bool) { if b { return } return 1 }`, is rejected by the checker with a message containing "must return a value". [src: spec/decisions/D-50-function-return-type-inference.md]
- FN-E8: A keyword used as a parameter name, such as `val`, is rejected as a parse error with a message containing "Expected Identifier". [src: spec/decisions/D-54-keyword-parameter-names.md; LEX-2]
- FN-E9: Calling a function with the wrong number of arguments is rejected by the checker with a message containing "expected N arguments" with the real count, as in "expected 2 arguments". [src: spec/decisions/D-57-function-call-error-checks.md]
- FN-E10: A `return` whose value does not match the declared return type is rejected by the checker with a message containing "declared return type". [src: spec/decisions/D-57-function-call-error-checks.md]
- FN-E11: A lambda with an untyped parameter and no typed context to infer it from, such as `val f = fn (x) -> x + 1`, is rejected by the checker with a message containing "Cannot infer parameter type". [src: spec/decisions/D-167-lambda-parameter-inference.md]
- FN-E12: A default value on a parameter, typed (`x int = 1`) or typeless (`x = 1`), is rejected by the checker with a message containing "default value", until the feature is designed. [src: spec/decisions/D-173-parameter-default-values.md]
- FN-E13: Declaring a second function with a name already declared in the same scope is rejected by the checker with a message containing "already declared", even when its parameter list differs, because Pino has no user-defined overloading. [src: spec/decisions/D-176-no-user-overloading.md; spec/decisions/D-018-redeclaration-in-same-scope.md]
- FN-E14: Reassigning or mutating the interior of a non-`mut` parameter (including lambda parameters, implicit `it`, and stdlib callback parameters) is rejected by the checker. [src: spec/decisions/D-180-mut-parameters-calls-and-closures.md]
- FN-E15: Omitting `mut` at a call site for a `mut` parameter, passing `mut` for a non-`mut` parameter, or passing an immutable binding, read-only field, or non-place rvalue expression as a `mut` argument is rejected by the checker. [src: spec/decisions/D-180-mut-parameters-calls-and-closures.md]
- FN-E16: Passing two `mut` accesses in the same call (including a mutating method receiver as one `mut` access, per FN-35) that share a root binding and are *proven* to overlap — meaning walking their place paths from the root reaches the end of one or both paths with every compared step proven equal and no unknown index-step pairs (such as `swap(mut a, mut a)`, `f(mut a, mut a:x)`, `f(mut v, mut v[i])`, `f(mut v[0], mut v[0])`, `f(mut v[i], mut v[i])` with immutable `i`, `a:merge(mut a)`, or `v[i]:hit(mut v[i])` with immutable `i`) — is statically rejected by the checker (`PN3226`). If the two paths share at least one index step (such as `f(mut v[0], mut v[0])` or `es[i]:hit(mut es[i])`), the message is `Cannot pass the same element of '<collection>' as two 'mut' arguments to <target>.` with help `use two different elements, or make one argument a plain read`. Otherwise (a whole value or a field, such as `swap(mut a, mut a)`, `f(mut a, mut a:x)` or `a:merge(mut a)`) the message is `Cannot use '<name>' twice as 'mut' in one call to <target>.` with help `pass it once as 'mut', or pass a copy for the other argument`. `<collection>` is the first identifier of the path as written, `<name>` is the shorter of the two paths as written (`a` for `f(mut a, mut a:x)`, `p:x` for `f(mut p:x, mut p:x)`), and `<target>` follows FN-34. [src: spec/decisions/D-180-mut-parameters-calls-and-closures.md; spec/decisions/D-184-disjoint-mut-slots.md]
- FN-E17: Capturing a `mut` parameter (or mutably capturing `self` inside a `mut fn`) inside a closure is rejected by the checker. [src: spec/decisions/D-180-mut-parameters-calls-and-closures.md]
